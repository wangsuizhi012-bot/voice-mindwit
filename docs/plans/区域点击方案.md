# 区域化点击 + 防误触 + 置顶 + 模板识图 实施方案（计划稿 v0.1）

> 状态：**计划稿，未实现**。目标是在现有 voice-assistant（语音→意图→执行）链路上，给"点击"加一层"空间坐标"能力，解决"说搜索框点不中、OCR 整屏慢、没有位置概念"三个短板。
> 提出人：用户（2026-08-14）。来源想法：屏幕分 4 区，按区域粗定位；防误触；点完置顶该程序；最好能像 Python 脚本那样"按图找图"。

---

## 一、要解决什么（动机）

当前 `click_target` 走三级定位：`控件树(uiautomation) → 记忆库(click_memory.json) → OCR(easyocr)`。

实测短板：
1. 口语词和控件名对不上就失败（"点搜索框"→记事本里没有这个文字控件）。
2. OCR 是全屏扫，慢、且易误中别处同名字。
3. 用户没有"大致位置"的表达方式，必须说得很准。

**本方案补的层**：把屏幕切成 4 块，先用"区域"做粗定位（你只要说"点左上"），再在区域内做精确定位（模板匹配 / 文字 / 控件树）。区域天然缩小了搜索范围，命中率更高、OCR 也不用扫全屏。

---

## 二、总体设计（四层）

```
语音 → 本地 LLM 出 JSON
  ├─ click_region {region, target?}   # 新增：区域粗定位 + 区内精确定位
  ├─ pin_top    {region}              # 新增：把该区域窗口置顶
  └─ click_target {target}            # 保留：精确文字控件仍可用
        ↓
  防误触门控（预览高亮 / 右键优先，待定）
        ↓
  执行：pyautogui 点击 / win32gui 置顶
```

## 三、模块拆分

### 3.1 分区模块 `region.py`（新增）
- `get_screen_regions()`：读 `pyautogui.size()` 得 `(W,H)`，按中线切四象限，返回每象限 `(x, y, w, h)` 与中心坐标。
  - TL 左上 `(0,0)-(W/2,H/2)`，中心 `(W/4,H/4)`
  - TR 右上 `(W/2,0)-(W,H/2)`
  - BL 左下 `(0,H/2)-(W/2,H)`
  - BR 右下 `(W/2,H/2)-(W,H)`
- 语音词映射：左上/左上方→`tl`，右上→`tr`，左下→`bl`，右下→`br`。
- 可扩展：六分（左半/右半/上半/下半）或九分宫格（留作 P4）。
- 接口：`region_center("tl")`、`region_box("tl")`、`region_from_words(text)`。

### 3.2 防误触机制（两种，待你拍板）
- **方案 A（推荐）：预览 + 二次确认**
  - 收到"点左上"→ 先在置顶小窗**高亮该象限**（画半透明框）+ 鼠标移到中心，**不真点**
  - 等你再说"确认 / 就这 / 点"才执行 left-click
  - 复用现有 `confirm_high_risk` 心智，但这次是**视觉化**的（你能看到要点的地方）
- **方案 B：右键优先**
  - 默认先发 `right-click`（一般只弹菜单、不触发主按钮），需真点时再说"确定"补 `left-click`
  - 更防误触但交互略怪，且右键会留下菜单要关

> 你原话"可以先右键"我理解为方案 B；但方案 A 的预览+确认在语音场景下更顺。两份都列了，**你定一个**。

### 3.3 置顶模块 `pin_top.py`（新增）
- `pin_window_at(x, y)`：`win32gui.WindowFromPoint((x,y))` 拿句柄 → `GetAncestor(GA_ROOT)` 取顶层窗口 → `SetWindowPos(hwnd, HWND_TOPMOST, 0,0,0,0, SWP_NOSIZE|SWP_NOMOVE)` 置顶。
- 失败回退：枚举前台窗口置顶。
- 依赖：`pywin32`（项目已装，现成可用）。
- 触发：① `pin_top` 独立指令；② `click_region` 执行后可选项"点完自动置顶该窗口"（配置开关）。

### 3.4 模板识图（区域内精确定位，P3）
- 维护 `templates/` 目录，存目标截图（如 `搜索.png`、`发送.png`）。
- `match_in_region(region, template)`：截取该象限 → `cv2.matchTemplate`（easyocr 已带 opencv，可复用）→ 返回最佳匹配中心。
- 语音："点左上角的搜索" → `region=tl` + `target=搜索` → 在 TL 象限内模板匹配。
- 模板来源（教学态延伸）：首次用手动框选 / 截图生成模板存入 `templates/`，后续复用——和现有 `click_memory.json` 思路一致，只是从"坐标记忆"升级到"图像记忆"。
- 依赖：`opencv-python`（已有）、`Pillow`（已有）。

## 十、主流方案调研对比与优化空间（2026-08-14 网上调研）

### 10.1 主流三大派

**A. 系统级语音控制（Windows Voice Access / Apple Voice Control）** — 最贴近"说话点屏幕"
- **编号覆盖（Number Overlays）**：说 `"Show numbers"`，屏幕所有可点控件被打上编号，说 `"Click 5"` 即点第 5 个。控件名说不清时用。
- **网格覆盖（Grid Overlay）**：说 `"Show grid"`，屏幕分成带编号的格子；说一个数字**钻进该格出更细的网格**，反复直到落到任意像素，再说 `"Click"`。**这是递归缩放网格，不是固定分区。**
- 来源：https://support.microsoft.com/en-us/topic/use-voice-to-interact-with-items-on-the-screen-e1b53c8a-7765-495a-9611-d9b37c008319 ；https://allthings.how/how-to-voice-control-your-windows-11-pc/

**B. 视觉 GUI Agent（Microsoft OmniParser / UFO / Claude Computer Use）** — 当前学术界/工业界主流
- **OmniParser**（microsoft/OmniParser，GitHub 24.8k★）：纯视觉，把截图解析成结构化 UI 元素。流水线 = YOLOv8/YOLOv9-E 检测可交互区 → 画边界框 + 唯一 ID（**Set-of-Marks**）→ OCR 抽文字 + BLIP-2 给图标写功能描述 → VLM（GPT-4V / Qwen2.5-VL / DeepSeek）输出"点哪个 ID"。V2 推理延迟降 60%。
- **Set-of-Marks (SoM) 范式**：在截图上叠编号框，让模型输出框号而非裸坐标——这是 2024 起 computer-use agent 的事实标准。
- 来源：https://github.com/microsoft/OmniParser ；https://hub.baai.ac.cn/view/43983 ；https://ainews.cool/ru/article/20260526-microsoft-omniparser-gui-agent
- **UFO**（微软 Windows 专用 agent）：优先用无障碍树（和你现有 uiautomation 同思路），配合 SoM。

**C. 传统 RPA 坐标/模板**（UI.Vision、TagUI）
- 录坐标或模板匹配回放，脆弱（窗口移动即废）——你已弃用的路线。

### 10.2 跟你的"4 区域"想法对比

| 维度 | 你的设想 | 主流做法 | 差异 |
|---|---|---|---|
| 空间定位 | 固定 4 象限，点区域中心 | Windows Voice Access **递归网格**（钻进格子再细分到任意像素） | 你的是"粗定位终点"，主流是"可无限缩放到单像素" |
| 元素识别 | 控件树→记忆库→OCR / 模板 | OmniParser **SoM 编号 + VLM 语义** | 你靠文字匹配，主流靠"看见+编号"让用户/模型选 |
| 防误触 | 预览+确认 / 右键优先 | 编号覆盖本身就是"先看见再点" | 一致，A 方案就是主流思路 |
| 置顶 | 点完置顶该程序 | 非主流功能；Voice Access 有 Maximize/Snap 等窗口管理 | 你的差异化点 |
| 按图找图 | 模板匹配（cv2） | OmniParser 训练好的检测模型（YOLO） | 模板匹配轻量但怕缩放/换肤；YOLO 鲁棒但要 GPU/模型 |

### 10.3 更好的优化空间（落到你项目）

1. **固定 4 区 → 递归网格（最高优先级，低成本高收益）**
   抄 Windows Voice Access 的 `Show grid`：屏幕先分 3×3（或 4×4）带编号格，说"格 7"钻进第 7 格再出细格，反复到目标。这比固定 4 区强太多——既能粗（"点右下"）又能细（任意像素），且不需新模型。建议 `region.py` 改成 `grid.py` 支持递归层级。

2. **控件树直接出 SoM 编号（比模板匹配更稳更省）**
   你已有 uiautomation 控件树，每个控件本来就有 rect + 名字。**别急着做模板匹配**，先把树上所有可点控件画编号框 + 在小窗列清单，用户说"点 5"就点第 5 个。这等于"零模型的 OmniParser-SoM"，比 cv2 模板匹配鲁棒（不怕主题/缩放），比 OCR 文字匹配准（控件名和你说的不一定同）。

3. **"按图找图"分两档**
   - CPU/轻量档（保留你的模板匹配）：适合固定图标、自绘 UI，零模型。
   - 想真正鲁棒：本地跑 **OmniParser-v2（YOLOv9-E）**，开源可本地、约 120ms(A100)，CPU 慢些但能检测图标/无文字控件——你 uiautomation 够不到的游戏/自绘界面就靠它。属 P4 重模型档，沿用你"暂缓重模型"的判断。

4. **重排定位优先级链**
   控件树(免费精确) → SoM 编号(用户选) → 递归网格(任意像素) → OCR/模板(兜底)。把"区域内精确定位"从单一 OCR 升级成这条链。

5. **防误触用"网格/编号预览"代替纯右键**
   方案 A（预览+确认）已对；可进一步：预览时直接画递归网格 + 高亮候选，比"先右键"直观，也和主流一致。

### 10.4 结论

- 你的"分区域 + 防误触 + 置顶"方向**和主流一致**，不是野路子。
- 最大可优化点：**固定 4 区升级成递归网格**（抄 Windows 自带能力，几乎零成本）；**控件树直接出 SoM 编号**（零模型版 OmniParser，比模板匹配更优）。
- "按图找图"用模板匹配作为轻量档没问题，真要强就上 OmniParser-v2 本地模型（你已定的"重模型暂缓"档）。
- 置顶是主流没有的差异化能力，可保留并宣传。
